Reverse Engineering

Taking Apart a Banking Application

I was given a locked archive and a hint. Inside was a desktop banking client. Decompiling it showed me exactly how it talked to its server, and that was enough to read every customer's balance.

Target
.NET desktop application
Decompiler
dnSpy
Interception
Fiddler
Also used
John the Ripper · ffuf · sqlmap

Getting into the archive

The starting point was a password-protected zip file and a letter naming the person it was meant for. Nothing else.

The letter was the clue. Rather than guessing passwords, I built a wordlist of every date of birth from 1920 to 2025 in the format the letter used, converted the archive into a crackable hash, and ran John the Ripper against the list. It matched, and the archive opened. Turning a password guess into a small, structured search is usually faster than any general wordlist.

A file that was not supposed to be there

Inside was a Windows application, and alongside it a .DS_Store file — a macOS folder-layout artefact that someone had packaged by accident. Those files list the names of everything that was in the folder when it was created, including files that are no longer there.

I wrote a small parser to pull the names out. The format stores strings as UTF-16, so a plain strings command misses most of them: 

# .DS_Store keeps names as UTF-16LE, so scan for both encodings
ascii_runs = re.findall(br"[ -~]{4,}", data)
utf16_runs = re.findall(br"(?:[ -~]\x00){4,}", data)

It recovered a filename that pointed straight at a credentials file. A leftover artefact from the developer's machine gave away part of the answer before I had touched the application.

Reading the application

The application shipped as a .NET assembly, which means it is not really compiled the way a C program is. It is bytecode that carries its own type and method names, so a decompiler can rebuild readable source. I opened it in dnSpy and worked through the form logic until I understood what the program actually did.

That gave me three things a black-box tester would have had to guess at:

  • The password is hashed on the client, using a key held inside the application, before anything is sent.
  • Login returns a token, and that token is what authorises later requests.
  • The token expires after 300 seconds, a detail sitting in code that would have looked like random failure from the outside.
Why this is the whole point

Anything shipped to the user is readable by the user. The key used to hash that password was inside the file on my own disk. Decompiling turned an unknown protocol into a documented one, and every step after this depended on it.

Finding the username

The credentials file gave me a password but no username. I knew the account holder's name from the letter, so I generated a wordlist of every common way an organisation turns a person's name into a login — first.last, initial plus surname, surname first, and the rest — and worked through it until one was accepted.

The traffic problem

Next I wanted to see the requests. Directory discovery with ffuf against the host revealed two endpoints, /login and /data, but calling them directly got me nowhere. I needed to watch the real client.

Burp Suite failed. The application checks the server's X.509 certificate and refuses to continue when a proxy sits in the middle, so the connection simply died. This is the same wall as certificate pinning on mobile, and it is where a lot of desktop testing stops.

Fiddler got through, and with traffic finally visible I could confirm what the decompiled code had already told me: the hashed password going out, the token coming back, and that same token being presented to /data to fetch balances.

What the server did wrong

Now that I could build valid authenticated requests, I tested the /data endpoint for injection, and it was vulnerable. Using sqlmap through the authenticated path, I extracted the user table — account names, password hashes, and balances for every customer, not only the one I had logged in as.

The first extraction came back misaligned, with values not matching across columns, so I reran it with different techniques until the rows were consistent. Believing the first output a tool gives you is how findings turn out to be wrong.

From there I cracked the recovered hashes offline and got working passwords for two administrator accounts, then totalled the balances held across specific customers to show the scale of what was exposed.

Where it stopped

I did not capture the final flag. Reaching it needed code execution on the host, and I tried several routes without success: local file inclusion through path traversal, log poisoning, and uploading a shell through the database. None of them landed.

Recording that matters. A report that only lists what worked is not an accurate picture of the target, and the paths that failed tell a defender which of their controls are actually holding.

What this shows

  • Decompiling a .NET binary and reading it well enough to rebuild an undocumented protocol.
  • Writing my own tooling when nothing off the shelf fits — the date wordlist and the .DS_Store parser were both a few lines that unlocked a whole stage.
  • Working around client-side certificate checks, and knowing to change tool rather than give up.
  • Chaining it end to end: locked archive, leftover artefact, decompilation, authentication, injection, offline cracking.
  • Reporting the failures next to the successes.
Note

Done against a deliberately vulnerable application built for a university penetration testing course. Account names, recovered passwords, and host details are deliberately left out.
