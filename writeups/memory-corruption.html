Memory Safety

Buffer Overflows and Memory Corruption

Writing past the end of a buffer does not just corrupt data. It can overwrite the note the program keeps about where to go next, and at that point the attacker decides what runs.

Languages
C / C++
Bug classes
Stack, heap, off-by-one, format string, integer
Defences
NX/DEP · ASLR · stack canaries
Finding them
Fuzzing · sanitizers

Why this still matters

C accounts for roughly half of all reported open-source security vulnerabilities. Not because C programmers are careless, but because of what the language is: direct pointer arithmetic, raw memory access, no automatic bounds checking, and manual memory management. It gives you full control and almost no safety net.

That combination is also why C sits underneath nearly everything — operating systems, network stacks, embedded devices, cryptographic libraries. The bugs are old, well understood, and still shipping.

How a program remembers where it was

To understand the attack you have to understand the stack. When a function is called, the program pushes a frame onto the stack containing the arguments, space for local variables, and — critically — the return address, which is where execution continues once the function finishes.

Local buffers live in that same frame. If the program copies more data into a buffer than it has room for, the extra bytes do not vanish. They keep writing into whatever is next in memory, and what is next is eventually the return address. Overwrite that and the function does not return where it was supposed to. It returns wherever the attacker's data says.

That is the whole idea. The bug is a memory error; the consequence is control of execution.

The main bug classes

ClassWhat goes wrong
Stack overflowWriting past a local buffer reaches saved control data such as the return address
Heap overflowWriting past a heap allocation corrupts the bookkeeping the allocator relies on
Off-by-oneA loop or size calculation that is wrong by exactly one byte, which is often enough
Format stringUser input used as a format specifier, letting an attacker read and write memory
Integer overflowA size calculation wraps around, so a correct-looking bounds check passes and a far too small buffer gets allocated
Use-after-freeMemory is used after being released, once something attacker-controlled may occupy it

Integer overflow deserves attention because it is the least obvious. The bounds check is there, it is written correctly, and it still passes — because the arithmetic feeding it wrapped around before the comparison happened.

Redirecting execution

Once memory can be corrupted, the next step is turning that into control. The direct route is overwriting the return address. Where a function pointer is stored in reachable memory, overwriting that works too.

Modern systems make injecting new code hard, so the established technique is to reuse what is already there: chain together fragments of the program's own existing instructions to build the behaviour you want, without introducing any new code at all. That is the idea behind return-oriented programming, and it exists specifically because the defence below closed the simpler path.

The defences, and what each one actually stops

  • NX / DEP marks memory as either writable or executable, never both. Data an attacker writes cannot be run as code. This is what forced attackers toward reusing existing code.
  • ASLR randomises where things sit in memory each run, so an attacker cannot rely on a fixed address. It does not fix the bug; it makes the address unpredictable — which is why an information leak that reveals one real address is so valuable, since it can undo the whole protection.
  • Stack canaries place a known value between the local buffers and the saved return address. Before returning, the program checks it is unchanged. A straightforward overflow has to write through the canary to reach the return address, so the program detects the corruption and stops.

Each of these raises the cost rather than removing the bug, and they matter most in combination. None of them makes unsafe code safe.

Finding the bugs

Most memory corruption is found by machines, not by reading code. The main approach is fuzzing: feed a program huge volumes of malformed input and watch for crashes, because in C a crash is usually a memory bug wearing a disguise.

  • Black-box fuzzing — throw input at the program with no view inside it. Simple, and it wastes most of its effort on inputs rejected immediately.
  • White-box fuzzing — use knowledge of the program's structure to build inputs that reach deeper paths.
  • Grammar-based fuzzing — generate input that is structurally valid, so it survives parsing and reaches the logic behind it. Essential for anything reading a defined format.
  • Coverage-guided fuzzing — measure which code each input reaches, keep the inputs that reach something new, and mutate from those. This is what made fuzzing genuinely effective, because it lets the fuzzer find its own way into the program instead of guessing.

Fuzzing pairs with sanitizers — AddressSanitizer, UndefinedBehaviorSanitizer, Valgrind — which instrument the program so that memory errors are caught at the moment they happen rather than whenever the damage eventually causes a crash. Without them, a fuzzer misses every bug that corrupts memory quietly. With them, the fuzzer finds the bug and points at the exact line.

Writing code that does not have these bugs

The defensive side is less dramatic and more effective: validate input lengths, check bounds explicitly, use the safer library functions that take a destination size, and turn on the compiler's hardening flags. Where the choice is available, a memory-safe language removes the entire bug class rather than mitigating it.

Finding a memory corruption bug in someone else's software carries an obligation. The responsible path is a private report to the vendor, a reasonable window to fix it, and publication afterwards. Understanding that process is part of the skill, not an optional extra around it.
