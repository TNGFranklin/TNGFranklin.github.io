Cryptanalysis

Reading Encrypted Data Without the Key

The server never showed me the decrypted message. It only said whether the padding was right or wrong. That single yes-or-no answer was enough to read everything.

Target
HTTP decryption endpoint
Cipher
AES-CBC, PKCS#7
Language
Python 3
Key required
None

The setup

The target had a /decrypt page. You sent it an IV and some encrypted data. It tried to decrypt them and told you if the padding at the end looked correct. It never showed you the message itself.

That looks safe. You only get one bit of information back, and it is about padding, not about the content. But one bit is enough.

Why it breaks

In CBC mode, each block of the message is made by taking the cipher's output and XOR-ing it with the previous block of encrypted data: 

P[i] = D(C[i]) ⊕ C[i-1]

Here is the important part. I fully control C[i-1], because I am the one sending it. The middle value D(C[i]) is fixed by the key. I do not know it, but it never changes. So if I can learn D(C[i]), I get the message for free by XOR-ing it with the real previous block.

The server hands me that value. I send a fake previous block and try all 256 possible values for its last byte. For exactly one of them, the last byte of the result becomes 0x01, which is valid one-byte padding, and the server says so. Now I know: 

intermediate[15] = guess ⊕ 0x01

That is one byte. To get the next one, I set the last byte so it becomes 0x02, then try all 256 values for the second-to-last byte, looking for valid 0x02 0x02 padding. I repeat this, growing the part I know, until the whole block is done. Sixteen bytes at up to 256 tries each is 4,096 requests per block. That is nothing.

The code

The main loop works backwards from the last byte. It sets the bytes I already know to the padding value I need, then tries every value for the next unknown byte: 

for pad in range(1, block_size + 1):
    pad_index = block_size - pad

    for guess in range(256):
        crafted = bytearray(C_prev)

        # set every byte I already know to the padding value I need now
        for j in range(pad_index + 1, block_size):
            crafted[j] = intermediate[j] ^ pad

        crafted[pad_index] = guess

        if validate_ciphertext(server, auth, crafted.hex(), b64(C_cur)):
            intermediate[pad_index] = guess ^ pad
            recovered[pad_index]   = intermediate[pad_index] ^ C_prev[pad_index]
            break

Two details matter here, and both are easy to get wrong:

  • Treat the IV as block zero. If I put the real IV at the front of my list of blocks, the first block of the message is recovered by the same code as every other block. No special case needed. Attacks that skip this quietly lose the first sixteen bytes.
  • Strip the padding at the end. The recovered message still has its PKCS#7 padding on it. The last byte tells you how many bytes to remove.
A catch

When attacking the last byte, there is a rare second answer that also works. The fake block can accidentally produce valid longer padding, such as 0x02 0x02. To be safe, change the second-to-last byte and ask again. If the server still says valid, the padding really was 0x01.

Result

The tool read the full message from multi-block encrypted data on the live server. You run it from the command line with the IV and the encrypted data as arguments. Speed depended on network delay, not on maths. The cryptography here is cheap. It is the number of requests that costs you.

What this shows

  • One bit of error information is a full break, if that bit depends on the secret data.
  • Giving different errors for different failures is a real bug, not a small detail. The fix is authenticated encryption such as AES-GCM, not a vaguer error message.
  • Knowing the maths behind a cipher mode is what turns "the server said no" into a way to read everything.
Note

This was done against a lab server set up for the exercise. The server address and login token have been removed from the code above.
