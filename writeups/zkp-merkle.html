Zero-Knowledge Membership Proofs

Prove you are on an approved list without saying which member you are. And make sure you can only do it once, without anyone keeping a record of who has already acted.

Proof system
Groth16
Hash
Poseidon
List size
Up to 65,536
Built with
Circom · snarkjs · Solidity

The problem

There is a conflict at the heart of anonymous membership. If you show an ID to prove you belong, you have just told everyone who you are. If you show nothing, then one person can act a thousand times and nobody can stop them.

The system needs both things at once: nobody learns who you are, and nobody can act twice.

How it is built

Every approved member has a private number, their secret. That secret is hashed into a public value called a leaf. All the leaves are combined into a tree, and the tree is squeezed down into one single value at the top, called the root. The root is the only thing stored in public. 

leaf      = Poseidon(secret, 0)
nullifier = Poseidon(secret, 1)
root      = the top of the tree of all leaves   // public, on the blockchain

Notice the 0 and the 1 in those two lines. The leaf and the nullifier come from the same secret, but the extra number keeps them separate. Because of it, neither value tells you anything about the other, but both are still tied to the same person.

I used Poseidon instead of SHA-256 because of how these proofs work. A proof system does its maths in a special way, and Poseidon is designed to fit that maths cheaply. SHA-256 does the same job but costs hundreds of times more work inside a proof.

What the proof actually says

ValuePublic?What it is for
secretPrivateYour credential
pathElementsPrivateThe other hashes needed to climb the tree
pathIndicesPrivateLeft or right at each step. Would reveal your position
rootPublicTies the proof to the approved list
nullifierPublicLets the system spot a repeat

The proof rebuilds your leaf from your secret, climbs sixteen steps up the tree, and checks that it arrives at the public root. It also checks that the public nullifier really was made from your secret. Anyone can verify all this. What they learn is only that somebody on the list made the proof, and nothing more.

The path directions must stay private. If you published them, you would be telling everyone your exact position in the tree, which never changes. That is a permanent nickname, and your anonymity is gone.

The blockchain side

uint256 root;
mapping(uint256 => bool) nullifierUsed;

The smart contract stores only two things. When you submit a proof it checks the proof against the stored root, checks that your nullifier has not been seen before, marks it as used, and then does the action. If you try again, it fails, because your secret always produces the same nullifier. You cannot make a different one.

A design detail

If the list does not fill the tree completely, the empty slots are filled with a fixed set of zero hashes rather than copies of real members. This keeps the root well defined for any list size, and makes sure an empty slot can never be mistaken for a real member.

Building it

Four separate tools have to agree perfectly here: Circom writes the proof rules, snarkjs does the setup and makes the proofs, solc compiles the checking contract, and Python ties it all together to deploy and test.

Most of the real difficulty is where these tools meet. If a number is stored slightly differently in the Python code than the proof rules expect, the proof fails. You get no error message that tells you why. So I wrote a file of known-good test values that both sides check against. That way I could change one part and immediately see which side was wrong.

The final version deploys to a real network and runs the whole thing end to end: build the tree, make the proof, deploy the contract, verify on chain, then try the same proof again and confirm it gets rejected.

What this shows

  • Turning a written specification into working proof rules, where every assumption has to be spelled out.
  • Choosing building blocks based on what they cost in the system you are using, not on what is familiar.
  • Thinking carefully about what each public value gives away. Getting the nullifier right and the path wrong is the difference between being anonymous and having a permanent nickname.
  • Getting four different tools to work together all the way to a live deployment, not just a passing test.
Note

Built as a university project on zero-knowledge proofs. Testing was done on a local blockchain and a public test network.
