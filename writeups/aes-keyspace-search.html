Cryptanalysis

Cracking a Five-Digit Password

The cipher was strong and the key was built correctly. It did not matter. The password behind it only had a hundred thousand options, so I tried them all.

Cipher
AES-256-CBC
Key from
PBKDF2-HMAC-SHA256
Rounds
10,000
Options to try
100,000

The file

The target was a file encrypted with OpenSSL from the command line. These files tell you a lot about themselves. They start with the text Salted__, then eight bytes of salt, then the encrypted data. Reading that header gives you everything you need to rebuild the key, except the password. 

if not data.startswith(b"Salted__"):
    raise SystemExit("Not an OpenSSL salted file")

salt       = data[8:16]
ciphertext = data[16:]

I knew from context that the password was a five-digit PIN. That changes the problem completely. Breaking AES-256 is impossible. Trying 100,000 PINs is easy.

Rebuilding how the key is made

OpenSSL builds both the key and the IV from one long output. It asks for 48 bytes: the first 32 are the AES-256 key, and the last 16 are the IV. Getting this split right is the whole trick. If you cut it in the wrong place, your code runs fine, finds nothing, and gives you no clue why. 

for i in range(0, 100000):
    pin = f"{i:05d}".encode()

    dk  = PBKDF2(pin, salt, dkLen=48, count=10000,
                 hmac_hash_module=SHA256)
    key = dk[:32]
    iv  = dk[32:48]

    cipher = AES.new(key, AES.MODE_CBC, iv)
    plain  = unpad(cipher.decrypt(ciphertext))

Knowing when you have won

All 100,000 wrong keys still produce output. It is just junk. So I needed a fast, cheap way to throw the junk away. Checking the padding does most of the work. A wrong key gives you random bytes at the end, and random bytes form valid padding only about one time in 256. 

def unpad(pt):
    if len(pt) == 0:
        return None
    pad = pt[-1]
    if pad < 1 or pad > AES.block_size:
        return None
    if pt[-pad:] != bytes([pad]) * pad:
        return None
    return pt[:-pad]

That still lets a few hundred wrong answers through over the whole run. So anything that survives gets a second check: the start of the text must be readable ASCII, or contain a word I expect. Two cheap checks in a row beat one expensive check.

Where the time goes

The AES part is almost free. Nearly all the time goes into 10,000 rounds of hashing per password. That is exactly what those rounds are for, and they do slow the attack down a lot. But against only 100,000 passwords, slowing it down is not enough to save you.

Result

I found the PIN and opened the file. The interesting part is not that it worked, but by how much. AES-256, with proper salting and proper rounds, fell in minutes on a laptop. The real protection on that file was about 17 bits, which is nothing.

What this shows

  • A key is only as strong as the password behind it. "AES-256" tells you nothing about how hard a file is to open.
  • Copying a tool's key setup exactly, down to the byte positions, is the difference between an attack that works and one that silently fails.
  • Putting a cheap check before an expensive one keeps big searches fast.
Note

Done against a file created for a lab exercise.
